# Ansible role: keycloak

Installs the Red Hat build of Keycloak operator (OLM Subscription, same
operator-then-instance split as `ansible/roles/argocd` and
`ansible/roles/external_secrets`), then applies the `keycloak` GitOps
Application (`gitops/apps/keycloak` -> local chart
`gitops/charts/keycloak`) that renders:

- the `Keycloak` CR (`k8s.keycloak.org/v2alpha1`) - one instance, demo scope;
- an `ExternalSecret` resolving the bootstrap admin credentials the `vault`
  role auto-generates at `secret/zuno/keycloak/admin`;
- an `ExternalSecret` resolving the Google OAuth client at
  `secret/zuno/google-oauth/client` (placeholder until an operator
  populates it - see `ansible/roles/vault/tasks/configure.yml`);
- the `KeycloakRealmImport` CR carrying the `zuno` realm: 5 groups, 11
  users, 5 per-agent OIDC clients and the `google` identity-provider broker.
  See `gitops/charts/keycloak/files/realm-zuno.json`.

Two integration fixes applied when wiring this against the other tracks'
work (not present in the original per-track build):

- `tekos-frontend` is a **confidential** client (`publicClient: false`,
  `secret: "${vault.tekos_frontend_client_secret}"`), not public like the
  other four - `components/agent-frontend` does a server-side authorization-code
  exchange (see its `internal/oidc/oidc.go`), which needs a client secret.
  The secret is self-generated by `ansible/roles/vault` at
  `secret/zuno/keycloak/tekos-frontend` and injected via the same
  `KC_VAULT_*` env-SPI mechanism as the Google IdP secret (see
  `templates/keycloak.yaml` / `templates/externalsecret-tekos-frontend.yaml`).
- Every user's `credentials[0].temporary` was flipped from `true` to
  `false`. `KeycloakRealmImport`'s non-interactive nature means a user with
  a temporary password can never complete the `UPDATE_PASSWORD` required
  action it triggers - the 20-scenario evaluation (`evaluations/tekos/`)
  authenticates each persona via a direct (ROPC) grant, which fails
  outright against a temporary credential. Passwords stay synthetic/demo
  values either way (ADR-0025).

Runs after `argocd` and `external_secrets` (which registers the
`vault-backend` `ClusterSecretStore` the two `ExternalSecret`s above
resolve against) - enforced by ordering in
`ansible/playbooks/{precheck,prepare,configure}.yml`.

## Operator package/channel assumptions

This environment has no live cluster to verify catalog contents against, so
`precheck.yml`/`prepare.yml` make a best-effort, clearly-flagged guess:

| Item | Assumed value | Verify with |
|---|---|---|
| OLM package name | `rhbk-operator` | `oc get packagemanifest -n openshift-marketplace \| grep -i keycloak` |
| Subscription channel | `stable` | `oc get packagemanifest rhbk-operator -o jsonpath='{.status.channels[*].name}'` - RHBK channels are commonly version-qualified (e.g. `stable-v26`); a bare `stable` alias may not exist |
| Operator Deployment name | `rhbk-operator-controller-manager` | `oc get deployment -n openshift-operators` |

If any of these differ on the target cluster, adjust the corresponding
task in `tasks/precheck.yml` / `tasks/prepare.yml` - each is annotated with
this same assumption inline.

## Google OAuth secret injection into the realm import (ADR-0014)

The Keycloak Operator's `KeycloakRealmImport` CRD takes a full, inline
`RealmRepresentation` under `spec.realm`. Unlike `Keycloak.spec.db`'s
username/password fields (which the CRD does let you point at a `Secret`
via `usernameSecret`/`passwordSecret`), there is no equivalent
secret-reference field for arbitrary `identityProviders[].config` entries -
so the Google client ID/secret can't be wired in as a native CRD
`secretKeyRef`.

Instead this uses Keycloak's own built-in **vault SPI in `env` mode**
(https://www.keycloak.org/server/vault), which is exactly designed for this
case: a realm file, config file, or admin-console mapper value written as
`${vault.<key>}` is resolved at runtime from environment variable
`KC_VAULT_<KEY-UPPERCASED-WITH-NON-ALPHANUMERICS-REPLACED-BY-UNDERSCORE>`.
Concretely:

- `gitops/charts/keycloak/files/realm-zuno.json`'s `identityProviders[0]`
  sets `config.clientId` to `${vault.google_client_id}` and
  `config.clientSecret` to `${vault.google_client_secret}`.
- `gitops/charts/keycloak/templates/keycloak.yaml` sets `KC_VAULT=env` on
  the Keycloak container (`spec.unsupported.podTemplate`) and populates
  `KC_VAULT_GOOGLE_CLIENT_ID` / `KC_VAULT_GOOGLE_CLIENT_SECRET` from the
  `google-oauth-client` `Secret` (itself populated by the
  `ExternalSecret` reading `secret/zuno/google-oauth/client` from Vault -
  ADR-0024, never a hardcoded value).
- Both `secretKeyRef`s are marked `optional: true` so the Keycloak instance
  still comes up before an operator populates the Google credentials - only
  the Google login button stays non-functional until then, consistent with
  the "operator action required" step already documented by
  `ansible/roles/vault/README.md`.

**Assumption flagged for review:** the env-var-naming transform above is
the documented behavior of Keycloak's `env` vault provider as of the
upstream/RHBK versions this was authored against; re-verify against the
exact RHBK version this cluster installs (`spec.unsupported.podTemplate` is
also, by its own naming, an unsupported/best-effort operator API - if a
future RHBK version exposes a first-class `spec.db`-style secret reference
for identity provider config, prefer that instead).

## Database

The `Keycloak` CR intentionally omits `spec.db`, so the operator falls back
to its bundled dev database. Acceptable for this demo (single instance, no
HA requirement - see MEMORY.md section 2's ~50-user scale), but not durable
across a database pod loss. Wiring the shared PostgreSQL instance (ADR-0015)
is a documented follow-up once the `postgresql` role/track exposes a stable
service name and credentials contract; track this alongside ADR-0112
(production-grade backup and recovery, v1).

## Namespace-per-agent alignment (ADR-0023)

This role's realm defines one OIDC client per agent frontend. The
namespace each client's frontend actually deploys into (owned by another
track) must match the client's `redirectUris`/`webOrigins` host and the
`agent.namespace` attribute already set on each client in
`realm-zuno.json`:

| Keycloak client | Agent namespace | Agent |
|---|---|---|
| `comage-frontend` | `zuno-agent-comage` | Comage (sales) |
| `tekos-frontend` | `zuno-agent-tekos` | Tekos (technical consultants) - the only agent live in v0 |
| `advantage-frontend` | `zuno-agent-advantage` | Advantage (sales admin) |
| `finage-frontend` | `zuno-agent-finage` | Finage (finance) |
| `arkos-frontend` | `zuno-agent-arkos` | Arkos (architects) |

If a namespace or Route hostname changes on the other track's side, update
`clusterBaseDomain`/the per-client `redirectUris` in
`gitops/charts/keycloak/files/realm-zuno.json` (and re-run
`make configure keycloak`) to keep the two in sync.

## Group model (this track's concrete v0 decision)

Earlier architecture sketches (`docs/architecture/identity-architecture.md`,
`docs/security/identity-and-access.md`, `MEMORY.md` section 5) referred to
groups as `agent_<name>` plus a `sales_admin` group. This role implements a
more specific persona-oriented scheme instead - `sales`, `consultant`,
`adv`, `finance`, `board` - each mapped to exactly one agent's OIDC client
via a client role (see `realm-zuno.json`'s `groups[].clientRoles`). This is
the authoritative v0 group model; the earlier docs describe an
earlier-stage sketch that this implementation supersedes. See
`platform/identity/README.md` for the full JWT/`groups`-claim contract
downstream services consume.
