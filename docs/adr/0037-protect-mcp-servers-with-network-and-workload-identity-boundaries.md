# ADR-0037: Protect MCP servers with network and workload identity boundaries

- **Status:** Implemented
- **Target:** v0
- **Date:** 2026-08-05
- **Decision owners:** Zuno Demo architecture team

## Context

Downstream MCP servers such as `sales-db` trust calls that are expected to originate from the central MCP Gateway. Without explicit network isolation and workload authentication, another pod in the cluster could attempt to call a server directly and bypass gateway policy.

## Decision

MCP servers must accept traffic only from the MCP Gateway and explicitly approved operational probes. Enforce this with OpenShift NetworkPolicy and service/workload identity. Direct agent-runtime-to-MCP-server paths are forbidden. Sensitive MCP servers must validate the gateway workload identity in addition to relying on network location.

## Alternatives considered

- Keep the current implementation unchanged and rely on conventions or documentation. Rejected because the reviewed code shows that implicit contracts already diverge from intended behavior.
- Defer the decision until all five agents are implemented. Rejected because this decision affects the platform contract and should be resolved before additional agents amplify the current pattern.

## Consequences

The gateway becomes a real security boundary instead of a convention. Operational debugging requires controlled access paths.

## Security considerations

Use least-privilege service accounts, disable unnecessary service account token automounting, and prevent namespace-wide implicit trust.

## Operational considerations

Add an acceptance test showing that a direct call to `sales-db-mcp` from an unauthorized namespace/workload is denied.

## Implementation state

**Implemented (2026-08-05), two independent layers.** `gitops/charts/mcp-sales-db/templates/networkpolicy.yaml`
restricts ingress to `sales-db-mcp`'s pods to the MCP Gateway's pods
specifically, by pod label - not a namespace-wide allow, even though both
live in `zuno-ai`. This is precisely why `zuno-ai` deliberately has no
namespace-level baseline `NetworkPolicy` (unlike `zuno-auth`/`zuno-data`/
`zuno-telemetry`, see `gitops/charts/namespaces/values.yaml`'s
`platformNamespaces` comment): Kubernetes unions the allowed ingress of
every `NetworkPolicy` selecting a pod, so a broad "allow same namespace"
rule would have silently defeated this restriction. Every other `zuno-ai`
workload (`agent-runtime`, `ai-gateway`, `mcp-gateway`, this chart's
`sales-db-mcp`, `models`) got its own equally precise `NetworkPolicy`
instead, as part of ADR-0052's pass.

Network location alone is not trusted as sufficient (Security
considerations above: "must validate the gateway workload identity in
addition to relying on network location"). A shared secret
(`secret/zuno/mcp/gateway-workload-token`, vault-generated by
`ansible/roles/vault/tasks/configure.yml`, resolved into both services via
`ExternalSecret` + `MCP_GATEWAY_WORKLOAD_TOKEN`) is sent as
`X-Zuno-Gateway-Token` on every `components/mcp-gateway/app/downstream.py`
call to sales-db-mcp, and validated (constant-time comparison,
`hmac.compare_digest`) by `components/mcp-servers/sales-db/server.py`
before the request body is even parsed - a missing or wrong token is a
`401`, distinct from a JSON-RPC-level tool error. This was a genuine gap:
the server's own prior docstring stated plainly "this server does not
re-validate the caller's JWT, it trusts the gateway's ADR-0011 policy
intersection already happened" - true for the end-user JWT, but nothing
previously verified the *caller itself* was the gateway.

Least-privilege service accounts (Security considerations: "least-privilege
service accounts, disable unnecessary service account token
automounting") landed together with ADR-0052's broader pass across the
same charts - see that ADR's implementation note.

Mandatory acceptance test (Operational considerations above):
`evaluations/tekos/security_checks.py`'s
`direct_call_to_sales_db_mcp_denied_without_gateway_token` calls
`sales-db-mcp` directly (bypassing the gateway, no
`X-Zuno-Gateway-Token`) and asserts `401` - it exercises the
workload-identity layer specifically, since an HTTP-level check can't
directly prove a `NetworkPolicy` denial (a blocked connection and an
unrelated failure look the same at that layer); the `NetworkPolicy` itself
is verified statically by `platform/security/check_workload_hardening.py`
against every chart's rendered manifests.

## Acceptance criteria

- The implementation is merged through the normal repository review process.
- Relevant documentation and `MEMORY.md` are updated to describe the implemented state rather than the target state.
- `make check` or component-specific automated tests demonstrate the behavior described in this ADR.
- Security-negative tests are included whenever the decision changes an authorization, identity, data-classification or trust boundary.
