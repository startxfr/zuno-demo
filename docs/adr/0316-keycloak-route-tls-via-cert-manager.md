# ADR-0316: Keycloak's Route gets a cert-manager-issued certificate via a hand-authored Ingress

- **Status:** Implemented
- **Target:** v0
- **Date:** 2026-08-10
- **Decision owners:** Zuno Demo architecture team

## Context

`ansible/roles/cert_manager` (chart `gitops/charts/cert-manager`) deploys
cert-manager and a Vault-backed `ClusterIssuer` (`vault-issuer`), but until
now nothing consumed it - `ansible/roles/cert_manager/README.md` explicitly
documented this as "infrastructure only," with wiring a real Route/service
to it left as a deliberate, opt-in follow-up.

Keycloak (`ansible/roles/keycloak`, chart `gitops/charts/keycloak`)
currently relies on OpenShift's default ingress wildcard certificate: its
`Keycloak` CR sets `spec.ingress.enabled: true`, which lets the RHBK
operator auto-generate the externally-facing Route.

Closing that gap for Keycloak specifically runs into a structural
mismatch: an OpenShift `Route`'s `spec.tls` has no `secretName`-style field
the way a Kubernetes `Ingress` does - `spec.tls.certificate`/`.key`/
`.caCertificate` must be literal PEM strings. cert-manager only knows how
to write PEM data into a `Secret`, so it cannot target a Route directly.
Compounding this, Keycloak's Route isn't even hand-authored in this repo
today - it's generated by the RHBK operator from the `Keycloak` CR, so
there's no existing template to attach cert-manager annotations to in the
first place.

## Decision

Stop letting the RHBK operator manage Keycloak's externally-facing object.
Set `Keycloak.spec.ingress.enabled: {{ .Values.ingress.operatorManaged }}`
(default `false`, `gitops/charts/keycloak/templates/keycloak.yaml`), and
hand-author a plain `networking.k8s.io/v1 Ingress`
(`gitops/charts/keycloak/templates/ingress.yaml`) annotated with
`cert-manager.io/cluster-issuer: vault-issuer`.

cert-manager's built-in ingress-shim watches that annotation and
creates/renews a `Certificate`, populating `spec.tls[].secretName`
(`keycloak-tls`) on the Ingress. OpenShift's own Ingress-to-Route
controller then auto-generates a shadow `Route` from the Ingress with the
certificate embedded, pinned to `edge` termination (not `reencrypt`) via
the `route.openshift.io/termination: edge` annotation - matching the
existing `edge`+`Redirect` pattern already used by
`gitops/charts/tekos/templates/route.yaml`.

`edge`, not `reencrypt`, is deliberate: `reencrypt` would require the
Keycloak pod itself to terminate TLS, but it deliberately stays plain HTTP
internally (`spec.http.httpEnabled: true`, `KC_PROXY_HEADERS=xforwarded`
trusts the terminating proxy's headers for scheme/host reconstruction).
Only the certificate's origin changes; the router-to-pod hop is unchanged.

`vault-issuer`'s backing PKI role (`ansible/roles/vault`'s
`pki/roles/cert-manager`) previously only allowed `zuno-demo.internal`/
`svc.cluster.local` - extended to also allow the cluster's real apps
wildcard domain (`${CLUSTER_BASE_DOMAIN}`, resolved earlier in
`ansible/roles/vault/tasks/install.yml` and injected into the
unseal-configure Job), since Keycloak's hostname
(`keycloak.<clusterBaseDomain>`) is the first cert-manager consumer
requesting a cert for a public-facing hostname.

No new `ClusterIssuer`/PKI role: `vault-issuer` is reused as-is, unlike
the deliberately isolated `vault-issuer-istio` (separate PKI role for the
mesh's SPIFFE trust root) - there's no stated reason for Keycloak's Route
to need its own PKI role/blast-radius isolation the way the mesh CA does.

## Alternatives considered

- **Leave `ingress.enabled: true` and bolt cert-manager annotations onto
  the operator-generated Ingress/Route out-of-band.** Rejected: operators
  that own a sub-resource typically do a full-object reconcile on every
  loop, so a foreign annotation/field added out-of-band would plausibly be
  stripped and re-fought every cycle. Owning the object in this chart's own
  templates removes that risk deterministically instead of depending on
  unverifiable assumptions about the RHBK operator's reconcile semantics.
- **Hand-author a `Route` directly plus `cert-utils-operator` (redhat-cop)
  to bridge the cert-manager Secret into the Route's `spec.tls`.** A valid,
  well-established pattern, but a bigger lift for no added benefit here: a
  new OLM Subscription, a new `startx`-alias vendored chart, a new
  `-d0`/`-d1` Application pair, and a new Ansible role
  (precheck/install/README triad) purely to bridge a Secret into a Route -
  versus reusing cert-manager's own already-installed ingress-shim feature
  and a first-class OpenShift mechanism (Ingress-to-Route sync). Kept as
  the documented fallback if the Ingress-to-Route TLS sync assumption below
  turns out not to hold on a live cluster.
- **`reencrypt` Route termination.** Rejected - would require the Keycloak
  pod to terminate TLS itself, which it doesn't and shouldn't; see
  Decision above.
- **A dedicated PKI role for Keycloak, mirroring `vault-issuer-istio`'s
  isolation.** Rejected as unnecessary: the mesh's SPIFFE trust root is
  isolated for a specific, stated reason (blast-radius separation between
  workload identity and general-purpose TLS); no equivalent reason applies
  to a single Route's serving certificate.

## Consequences

`gitops/charts/keycloak/templates/keycloak.yaml`'s `spec.ingress.enabled`
now tracks `.Values.ingress.operatorManaged` (new value, default `false`)
instead of being hardcoded `true`. A new template,
`gitops/charts/keycloak/templates/ingress.yaml`, and new `values.yaml`
keys (`ingress.operatorManaged`, `.backendServiceName`,
`.backendServicePort`, `.tlsSecretName`) exist. `ansible/roles/vault`'s
`pki/roles/cert-manager` allow-lists the cluster's real apps domain in
addition to the internal-only domains it previously allowed.
`vault`/`tekos` are unaffected - they still rely on the OpenShift default
wildcard certificate; extending them to `vault-issuer` remains a separate,
opt-in follow-up.

See [Standard clauses](README.md#standard-clauses) for Migration/evolution
and Acceptance criteria.

## Security considerations

No change to the trust boundary of the certificate itself: `vault-issuer`
signs from the same self-signed internal Vault PKI root
(`common_name=zuno-demo.internal`) already used by `vault-issuer`'s other
(currently nonexistent) consumers, so browsers won't trust the chain out
of the box - not a regression versus the OpenShift default wildcard cert
on a demo cluster (also typically self-signed), just a change of issuer.
No privilege escalation: `ingress.enabled: false` only stops the RHBK
operator from managing the Route/Ingress object; it does not change what
the Keycloak pod itself is permitted to do.

## Operational considerations

**Load-bearing, unverified assumption:** that OpenShift's Ingress-to-Route
controller actually copies the cert-manager-populated Secret's
`tls.crt`/`tls.key` into the shadow Route's `spec.tls`, and keeps it
synced across cert-manager's periodic renewals. This is documented
OpenShift behavior, not exercised end-to-end here (no live cluster, no
vendored CRD/controller source to confirm against). If it doesn't hold in
practice, pivot to the `cert-utils-operator` fallback described above. See
`ansible/roles/keycloak/README.md`'s "External TLS via cert-manager" and
"What's unverified against a real cluster" sections for this and the
remaining smaller unverified items (backend Service name/port, whether the
RHBK operator still creates the Service with `ingress.enabled: false`,
whether the target OpenShift version's router honors a bare `Ingress`
without an explicit `ingressClassName`).

Rollout order: the Vault PKI role change must land and apply before the
Keycloak chart change, or cert-manager's CSR against `vault-issuer` will
be rejected as out-of-domain. `day0_components`
(`ansible/playbooks/day0_install.yml`) already runs `vault` well before
`keycloak`, so no new cross-role ordering was needed beyond the PKI role
fix itself.
