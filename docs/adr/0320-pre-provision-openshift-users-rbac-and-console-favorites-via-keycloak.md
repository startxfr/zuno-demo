# ADR-0320: Pre-provision OpenShift users, RBAC and Console favorites via Keycloak

- **Status:** Implemented — see `gitops/charts/openshift-oauth/`, `gitops/charts/openshift-rbac-groups/`, `gitops/charts/console-favorites-provisioning/`, `gitops/charts/keycloak/files/realm-zuno.json`. Note: the console-favorites JSON templates are still `_UNVERIFIED_PLACEHOLDER` pending capture from a live Console session.
- **Target:** v0
- **Date:** 2026-08-11
- **Decision owners:** Zuno Demo architecture team

## Context

ADR-0012 established Keycloak as this platform's central identity provider; ADR-0040 built a two-dimension group model on top of it in `gitops/charts/keycloak/files/realm-zuno.json` - `agent_<name>` entitlement groups crossed with business-role groups (`sales`, `sales_admin`, `consultant`, `adv`, `finance`, `board`) that gate access to the five agent frontends. Nothing in this repo today creates OpenShift `User`/`Group` objects, cluster or namespace RBAC bindings driven by Keycloak group membership, or OpenShift Web Console preferences - all three are new territory: no `OAuth`, `Group`, cluster-scoped `RoleBinding`, `ConsoleLink` or Console `user-settings-*` `ConfigMap` exists anywhere in `gitops/` or `ansible/`.

A separate, orthogonal need exists alongside the agent-frontend personas: platform/cluster operators need OpenShift Console and `oc` access, gated by four functional profiles - platform administrator, Zuno administrator, AI developer, AI Ops - each mapped to a Keycloak group (`admin`, `zuno-admin`, `aidev`, `aiops`) and a Kubernetes RBAC scope. The Console additionally lets each user pin namespaces as favorites, stored in a per-user `ConfigMap` (`user-settings-<UID>`) in `openshift-console-user-settings`, keyed by the user's `metadata.uid`. That UID does not exist until the `User` object is created - by default, only at first successful login - so favorites cannot be seeded ahead of a user's first Console visit without pre-creating the `User` first. `mappingMethod: add` on the OIDC identity provider is required so a later Keycloak login attaches to an already-existing, pre-created `User` instead of creating a duplicate.

This ADR targets OpenShift 4.22 (ADR-0319, which supersedes ADR-0002's 4.20 target for this reason).

## Decision

### Keycloak realm changes

Add four new top-level groups to `gitops/charts/keycloak/files/realm-zuno.json`: `admin`, `zuno-admin`, `aidev`, `aiops`. These are a third dimension, orthogonal to ADR-0040's `agent_<name>`/business-role groups - they gate platform/cluster access, not agent-app access, so no restructuring of the existing groups is needed.

Add a new confidential OIDC client `openshift` to the same realm file, following the same pattern already used for `tekos-frontend` (`publicClient: false`, server-side authorization-code exchange) rather than the four public agent-frontend clients - OpenShift OAuth does its own server-side code exchange, the same shape. Attach a client scope mapping the `groups` claim (`Group Membership` mapper, `Full group path: OFF`, added to ID token/access token/userinfo) - same mechanism already used for the agent frontends' `groups` claims.

The client secret is seeded in Vault by `ansible/roles/vault/tasks/install.yml` (new key `zuno/keycloak/openshift-client`, auto-generated, alongside the existing `keycloak/*` entries) and synced into `openshift-config` by a new `ExternalSecret`, resolved the same way `zuno/keycloak/tekos-frontend` already is. No `oc create secret --from-literal` step - that would violate ADR-0024's Vault-only credential rule, which every existing Keycloak-adjacent secret (admin bootstrap, Google OAuth client, `tekos-frontend` client secret, demo-personas password, Postgres app credentials) already follows.

### OpenShift OAuth configuration

A cluster-scoped `config.openshift.io/v1 OAuth`/`cluster` singleton adds an `identityProviders[0]` entry: `type: OpenID`, `mappingMethod: add`, `claims.groups: [groups]`, `clientID: openshift`, pointing at the `zuno` realm's issuer and the Vault-sourced client secret above.

### RBAC - static, no reconciliation needed

OpenShift OAuth already synchronizes `Group` membership from the token's `groups` claim on every login (`mappingMethod: add`) and already auto-creates the `User` object at first login if none exists. RoleBindings that target a `Group` by name therefore need no active reconciliation - they only need to exist, and GitOps already re-applies them whenever the namespace/group set changes. A new chart, `gitops/charts/openshift-rbac-groups`, renders:

- a `ClusterRoleBinding` binding `admin` to `cluster-admin` (full cluster-admin, no narrower role - the platform-administrator profile is intended to have unrestricted cluster access);
- a `RoleBinding` per namespace binding `zuno-admin` to the `admin` ClusterRole, generated by a Helm `range` over every namespace carrying the label `zuno.io/managed: "true"`;
- a `RoleBinding` binding `aidev` to `edit` in `zuno-ai-build`;
- `RoleBinding`s binding `aiops` to `edit` in `zuno-ai-build` and `zuno-ai-run`.

`gitops/charts/namespaces/values.yaml` gains `zuno.io/managed: "true"` on the five `namespaces:` agent entries (`zuno-agent-comage/tekos/advantage/finage/arkos`) and on seven `platformNamespaces:` entries (`zuno-auth`, `zuno-data`, `zuno-vault`, `zuno-monitoring`, `zuno-ai-build`, `zuno-ai-run`, `zuno-mesh`) - twelve namespaces total under `zuno-admin`. A future `zuno-*` namespace only needs this label to inherit `zuno-admin` RBAC on its next GitOps sync; no controller or job is needed for this part.

`aidev` and `aiops` are deliberately pointed at the platform's real, already-purposed `zuno-ai-build` (in-cluster build pipeline producing this platform's component images) and `zuno-ai-run` (shared Agent Runtime/AI Gateway/MCP Gateway runtime for all five agents) - not new, dedicated sandbox namespaces. This is an accepted, explicit trade-off: anyone in `aidev`/`aiops` gets `edit` on the platform's actual CI pipeline and the shared multi-agent runtime, a materially larger blast radius than a per-team sandbox would carry. Documented here rather than deferred, per this decision's own scope.

### Console favorites provisioning - the one component that needs active reconciliation

Unlike RBAC, this genuinely needs a running process: a new Keycloak user can appear at any time, not only at deployment, and their favorites must exist before their first Console visit - which requires knowing their OpenShift `User` UID ahead of that visit, which requires pre-creating the `User`.

New Ansible role `ansible/roles/console_favorites_provisioning`, following the existing role skeleton (`README.md`, `tasks/{precheck,install,uninstall}.yml`, applied via the same `apply_gitops_app.yml` task every other Day 0 role uses - see `ansible/roles/keycloak`). It installs a new GitOps chart deploying:

- a `ServiceAccount` and `ClusterRole`/`ClusterRoleBinding` scoped to exactly what the reconciler needs - `create`/`get`/`patch` on `users.user.openshift.io` (cluster-scoped), `create`/`get`/`patch` on `configmaps`/`roles`/`rolebindings` in `openshift-console-user-settings`, `get`/`list` on `namespaces` (to resolve `zuno.io/managed=true` for `zuno-admin` favorites). Not `cluster-admin` - the provisioner itself stays least-privilege even though the `admin` group it provisions for is not;
- a `CronJob` (the first in this repo - every existing Job here, e.g. `gitops/charts/sql-schema/templates/job-schema-apply.yaml`, is one-shot) running on a short, configurable interval. Each run: queries the Keycloak Admin REST API (a dedicated Keycloak service-account client, credentials Vault-seeded and `ExternalSecret`-synced the same way as everything else in this realm) for users and group membership; for any user in `admin`/`zuno-admin`/`aidev`/`aiops` without a matching OpenShift `User`, creates one; reads back `metadata.uid`; resolves the profile's namespace list using the *same* `zuno.io/managed=true`/`zuno-ai-build`/`zuno-ai-run` mapping the static RBAC chart uses, so both stay derived from one source of truth; creates (never overwrites) `ConfigMap user-settings-<uid>` seeded with `console.favorites`, a `Role` and `RoleBinding` scoping that `ConfigMap` to the user, all three carrying `ownerReferences` pointing at the `User` object so Kubernetes garbage-collects them automatically if the `User` is ever deleted.

**Idempotency requirement, not present in the original draft this ADR is based on:** because this now runs repeatedly rather than once, the reconciler must only set `console.favorites` when it creates the `ConfigMap`, never on a subsequent reconciliation pass. A one-shot provisioner has no way to clobber a user's own later customization; a periodic one does, and must be written to avoid it.

`console.favorites`'s internal format stays out of this reconciler's own logic, per the same reasoning the original draft used: four template accounts (`template-admin`, `template-zuno-admin`, `template-aidev`, `template-aiops`) are configured once through the real Console, and their captured `console.favorites` values are checked into the new chart as plain (non-secret) template files - favorites are UI data, not credentials, so no Vault involvement is needed for them.

### Demo personas

Four new anonymized personas are added to `gitops/charts/keycloak/files/realm-zuno.json`, one per new group (e.g. `platform-admin-01`, `zuno-admin-01`, `ai-dev-01`, `ai-ops-01`), `credentials[0].temporary: false`, password `${vault.demo_personas_password}` - the same shared Vault-generated secret ADR-0041's thirteen existing personas already use, no new Vault path required.

## Alternatives considered

- **Dedicated sandbox namespaces for `aidev`/`aiops`** instead of the existing `zuno-ai-build`/`zuno-ai-run`. Rejected for this decision: reuses the platform's real build/runtime namespaces instead, accepting the wider blast radius as documented above rather than introducing new namespaces.
- **A narrower role than `cluster-admin` for the `admin` group.** Rejected: the platform-administrator profile is intended to have unrestricted cluster access, matching the original profile table.
- **One-shot Day 0 provisioning only**, matching the original draft. Rejected: it would only cover users that already existed in Keycloak at deploy time, leaving later-added users without pre-seeded favorites until a manual re-run - the periodic `CronJob` above closes that gap.
- **A dedicated Kubernetes controller** reconciling `User`/`Group`/RBAC/favorites, as a possible future evolution. Rejected for v0 as unnecessary complexity given the simple, deterministic reconciliation loop above is sufficient; revisit if the CronJob's polling interval or API load ever becomes a real constraint.

## Consequences

Two new GitOps charts (`gitops/charts/openshift-rbac-groups`, and the chart applied by `ansible/roles/console_favorites_provisioning`) and one new Ansible role join the Day 0 sequence. `gitops/charts/namespaces/values.yaml` gains a new label dimension (`zuno.io/managed`) that both the static RBAC chart and the CronJob's namespace-resolution logic depend on - keeping a namespace off that label silently excludes it from `zuno-admin` RBAC and from `zuno-admin` favorites alike, which is the intended behavior but must be kept in mind when onboarding a new `zuno-*` namespace. `realm-zuno.json` grows a third group dimension and four more demo personas. This is this repo's first `CronJob`; its RBAC, secret-handling and idempotency requirements above set the pattern for any future recurring reconciliation job.

See [Standard clauses](README.md#standard-clauses) for Migration/evolution.

## Security considerations

The `admin`→`cluster-admin` binding is a deliberate, explicit grant of unrestricted cluster access - not an oversight, and should be reviewed if this profile's real-world membership ever grows beyond a small trusted set. `aidev`/`aiops` getting `edit` on `zuno-ai-build`/`zuno-ai-run` is likewise an accepted, documented trade-off rather than a default. The favorites reconciler's own `ServiceAccount` stays least-privilege (no `cluster-admin`, no write access outside `openshift-console-user-settings` and `User` creation) even though it provisions resources for groups that do have broader rights. Favorites remain UI-only preferences, never an authorization mechanism - their absence must never be read as a denial and their presence must never grant anything beyond what RBAC already grants, matching this repo's existing security posture. All new credentials (OIDC client secret, Keycloak service-account credentials for the reconciler) go through Vault + External Secrets Operator (ADR-0024) - no literal secret values in Git or in `oc create secret` invocations. The periodic reconciler must not overwrite an existing `console.favorites` `ConfigMap` (see idempotency requirement above) - failing to enforce this turns a UI convenience feature into a recurring data-loss bug for any user who customizes their own favorites.

## Operational considerations

The `CronJob`'s polling interval is a tunable Helm value; start conservative (e.g. every 5-10 minutes) and adjust based on observed Keycloak Admin API load. Errors reaching the Keycloak Admin API or the OpenShift API must not silently skip a user permanently - the next scheduled run should retry. `ansible/roles/console_favorites_provisioning/README.md` should document the one-time manual step of capturing each profile's `console.favorites` template from a real Console session against a template account, the same "operator action required" pattern `ansible/roles/keycloak/README.md` already uses for the Google OAuth client secret.
