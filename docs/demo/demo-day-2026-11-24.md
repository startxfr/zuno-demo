### MaaS budgets

**MaaS budgets: all subscription limits counted since 2026-11-20 12:27 UTC.**

**What happens.** The gateway's wasm EnvoyFilter was stuck at generation 3 from 2026-11-05 (3.9 MB desired, over the request limits of 3 MiB for the API and 2 MiB for gRPC), so 11 of 29 limits were never counted. [WP-314](../roadmap/work-packages/wp-314-fit-the-maas-gateway-wasm-config-under-1-4-mb.md) cut the routes to 3 matches per model and the subscriptions from 28 to 17; the filter is now at generation 4, 674,956 bytes, and 20 limits are counted (the 17 subscriptions, the default deny and the 2 workstation limits). WP-315 then regrouped the subscriptions on the evening of the same day (measured at 15:33 UTC: generation 14, 549,033 bytes, 15 limits counted, which are the 12 subscription limits, the default deny and the 2 workstation limits; 0 NOT USED). What changed on stage: the subscriptions are four usage tiers (WP-315): `<model>-platform` (the ai-gateway and Praxis, separate counters, 1,000,000 tokens an hour), `<model>-service` (Lightspeed and the stress identity, 200,000), `gpt-oss-20b-builders` (the three operator groups, 5,000,000) and `gpt-oss-20b-business` (`/sales`, 5,000, gpt-oss-20b only); there is no `-agents` subscription. The sales contrast was tested live on 2026-11-20 with the twin `test-stress-sale-01`: 200 on gpt-oss-20b with the sales counter moving (5,000 to 4,925; the subscription was named `gpt-oss-20b-sales` then and is `gpt-oss-20b-business` since the tiers), 403 on qwen36-27b-instruct.

**On stage.** Say the budget. A live over-budget 429 on a MaaS subscription is still not part of the show: the ai-gateway's own per-persona ledger of [the quotas scenario](scenarios/governance/quotas.md) is the one to show. A Praxis client never sees a MaaS 429, because a Praxis 429 falls back to the direct step.

**Evidence.** WP-314 checks of 2026-11-20 (`python3 platform/models/check_maas_wasm.py`: 20 limits COUNTED, 0 NOT USED); 14 of 14 golden-path probes PASS afterwards; `make d2 check agents` on agents v1.1.7 passes after the change (quality 18/19, security 14/14, gate checks 5/5; the one failure, the RAG citation, predates it). Before the change: 2026-11-19 15:53 UTC operator log "failed to update envoyfilter object ... Request entity too large: limit is 3145728"

### SaaS models and their keys

**What happens.** The ai-gateway and Praxis read each provider key once, at pod start: Mistral (`mistral-large-4`), Mistral Codestral (`codestral-latest`, behind Zuno Code) and OVHcloud (`gpt-oss-120b`). An expired key gives a 401 from the provider, and the call falls back to the local gpt-oss-20b. On 2026-11-19 the Codestral key expired and was renewed the same day; the ai-gateway rolled at 16:26 UTC and Zuno Code answers from `codestral-latest` again.

**On stage.** If Zuno Code is answered by gpt-oss-20b instead of Codestral, say that the gateway kept the user working on the local model. Do not rotate a key inside the freeze: a new key needs a roll ([key rotation runbook](../platform/saas-provider-key-rotation.md)).

**Evidence.** Golden path 2026-11-19 16:31 UTC: zuno-code "served by codestral-latest"

### GPU slices are all taken

**What happens.** The `zuno-ai-run` quota allows 3 `mig-1g.24gb` and 2 `mig-2g.48gb` slices, and all 5 are used. `mig-1g.24gb`: embeddings, gpt-oss-20b, qwen3.5-9b. `mig-2g.48gb`: qwen3.5-9b-wesh, qwen3.6-27b-instruct. A rolling update of a model cannot start its new pod: it waits for a free slice. A model pod that is deleted gets its slice back when the old pod is gone. Measured start to Ready: gpt-oss-20b about 3 minutes, qwen3.5-9b and qwen3.5-9b-wesh about 6 minutes, qwen3.6-27b-instruct about 13 minutes.

**On stage.** No model roll or restart inside the freeze. If a model is not Ready, the gateway answers 503 "no eligible provider": say that it refuses rather than sending restricted data to SaaS (the sovereignty rule). Do not wait on stage for qwen3.6-27b-instruct.

**Evidence.** Pod start and Ready times read on 2026-11-19

### Keycloak brute-force lock

**What happens.** The realm `zuno` locks a user after 30 failed sign-ins (`failureFactor` 30). The wait starts at 60 s and grows to at most 15 minutes. The lock is temporary, and failures are counted over 12 hours. A locked user sees the same "Invalid username or password" as a wrong password.

**On stage.** Sign every persona in once before the demonstration. If a persona is refused with the right password, an administrator of realm `zuno` clears the lock: admin console, Users, the user, then switch off the temporary lock. Or wait up to 15 minutes. Probes and stress runs use the `eval-*` and `stress-*` copies, never a demo persona.

**Evidence.** Settings in `gitops/charts/keycloak/files/realm-zuno.json`. On 2026-11-19 a stress copy was refused once during a run (cause not established)

### Sidecar log noise

**What happens.** The `istio-proxy` container logs "failed to generate secret for proxy from file ... service-ca.crt: no such file or directory" about every 15 s. It appears in the ai-gateway and in every `zuno-ai-run` pod that does not mount its ServiceAccount token (aap-mcp, confluence-mcp, diagram-render, git-forge-mcp). The 12 KServe DestinationRules point `caCertificates` at that mount.

**On stage.** Benign: calls are not affected. If logs are shown on stage, use the application container, not `istio-proxy`.

**Evidence.** Seen before and after the 2026-11-19 rebuild of the gateways, on pods that were not touched

### Lightspeed and its tools

**What happens.** Since Lightspeed 2.0 every tool result is screened by a classifier that asks the active model, gpt-oss-20b, for a strict JSON answer. About one such call in two comes back empty on this model server; after three attempts Lightspeed stops with "the tool-result safety inspection could not be completed". The recording of 2026-11-17 passed by chance.

**Since 2026-11-20, 19:17.** The screening is switched off in the `lightspeed-config` chart (`toolResultInspection.enabled: false`). The tools still run with the signed-in user's own rights, and the approval of tool calls is unchanged. It is switched on again after the demonstration, once an option of the model server has been tested.

**On stage.** Nothing to do. If the message appears, the setting came back: ask a question that needs no tool, or move on. See [the Lightspeed scenario](scenarios/experiences/lightspeed.md).

**Evidence.** 2026-11-20: three recordings out of three failed on the question that lists the pods of `zuno-ai-run`, with every model call answered 200; after the change, three calls out of three pass through the API.

### Kuadrant operator errors

**What happens.** The Kuadrant operator logs "failed to update envoyfilter object" on every HTTPRoute, Gateway or ConfigMap change. This is the cause of the MaaS budgets line above. Restarting the operator does not help (tried on 2026-11-19).

**Since 2026-11-20.** The cause is fixed by [WP-314](../roadmap/work-packages/wp-314-fit-the-maas-gateway-wasm-config-under-1-4-mb.md): at 15:33 UTC the check found no failed update in 30 minutes. The operator can still log "the object has been modified" (an optimistic conflict that it retries); that message is not a failure.

**On stage.** Nothing to do. Do not touch the Kuadrant operator inside the freeze.

**Evidence.** Operator log, 2026-11-19
