## 1. Client namespaces: egress NetworkPolicies and EgressFirewall

Every namespace also carries `zuno-default-deny-other-namespaces`
(**Ingress only**, from same-namespace pods and the `ingress` policy group).
It does not restrict egress. Egress is restricted only where an Egress
NetworkPolicy or an EgressFirewall exists, as below.

| Namespace | Egress NetworkPolicy | EgressFirewall `default` | Anything besides zuno-ai-run:8080 / Keycloak? |
|---|---|---|---|
| zuno-openwebui | `open-webui-egress` (all pods): DNS (openshift-dns 5353), zuno-ai-run TCP 8080, **0.0.0.0/0 TCP 443 except 10.128.0.0/14 and 172.30.0.0/16** | Allow `keycloak.apps.demo333.startx.fr` 443; Deny 0.0.0.0/0 | Only Keycloak (the firewall closes the policy's public 443). |
| zuno-kagent | `kagent-egress` (all pods): DNS, **same namespace (all ports)**, zuno-data 5432, three control-plane IPs 6443, 0.0.0.0/0 443 (same excepts). `zuno-token-proxy`: zuno-ai-run 8080, 0.0.0.0/0 443, DNS | Allow Keycloak 443; Allow 3 control-plane /32 on 6443; Deny 0.0.0.0/0 | Kubernetes API (6443) and zuno-data Postgres (5432, NetworkPolicy only; the firewall does not list it because it is in-cluster). |
| zuno-dify (incl. token-proxy) | `dify-egress` (all pods): DNS, same namespace, zuno-data 5432, 0.0.0.0/0 443 (same excepts). `zuno-dify-knowledge`: only to token-proxy 8080 and DNS. `zuno-token-proxy`: zuno-ai-run 8080, 0.0.0.0/0 443, DNS | Allow Keycloak, `s3.eu-central-1.amazonaws.com`, `zuno-demo-dify.s3.eu-central-1.amazonaws.com` (all 443); Deny 0.0.0.0/0 | S3 (two names) and zuno-data Postgres. |
| zuno-unifai | **none** (its NetworkPolicies are ingress only: `unifai-internal-apis`, `unifai-rag-clients`, `unifai-stack`) | Allow control-plane nodes 6443, Keycloak, `unifai-identity-zuno-unifai` route, `startxfr.atlassian.net`, S3 (2 names + about 22 S3 CIDRs), docs.redhat.com, raw.githubusercontent.com, argo-cd.readthedocs.io, helm.sh, github.com, api.github.com, codeload.github.com (all 443); Deny 0.0.0.0/0 | Yes, a wide list; **zuno-ai-run is not in the firewall** (in-cluster, so reachable by the absent egress policy). |
| zuno-claw-consultant-02 | `assistant-egress` (claw pods): only to `claw-proxy` 8080 and DNS (any namespace, 53/5353). `assistant-proxy-egress` (claw-proxy): `to: null` TCP 443 (**any destination**), DNS, zuno-ai-run 8080 | Allow control-plane 6443; Allow `keycloak.apps.demo333.startx.fr` (all ports); Deny 0.0.0.0/0 | The proxy's open 443 is closed to Keycloak only by the firewall. |
| zuno-claw-sale-01 | identical to consultant-02 | identical to consultant-02 | same |
| zuno-world-model | **none** (ingress only) | **none** | **Yes: no egress restriction at all** (no EgressFirewall, no egress NetworkPolicy). |

Only zuno-openwebui is limited to exactly zuno-ai-run:8080 plus Keycloak. For
the others, an extra route to a second gateway in zuno-ai-gateways (a new
namespace) would need: a new egress rule in kagent-egress / dify-egress /
the token-proxy policies / claw proxy policy / open-webui-egress, **and** no
EgressFirewall change (the firewall only denies external CIDRs; in-cluster
pod traffic is not filtered by it). unifai and world-model have no egress
policy to extend.

No AdminNetworkPolicy and no BaselineAdminNetworkPolicy exist.

clients' side by the ai-gateway policy, and it needs its own ingress policy;
the six client namespaces already carry the `experience-client` label that
mcp-gateway also uses.

## 3. Ingress peers of the four local model workloads and zuno-redis

All four are in `zuno-ai-run`; the workload port is **8000**. Common to all
(selector `app.kubernetes.io/name=<model>`, `kserve.io/component=workload`):

- pods `ai-gateway` (same namespace), and openshift-ingress pods of Gateway `maas-default-gateway`: TCP 8000
- openshift-monitoring, openshift-user-workload-monitoring and redhat-ods-monitoring: TCP 8000

Per model:

| Model | Extra ingress peers |
|---|---|
| qwen36-27b-instruct | namespace openshift-lightspeed (8000) |
| gpt-oss-20b | namespace openshift-lightspeed (8000) |
| qwen35-9b | pods `evalhub` evaluation-job of `zuno-evalhub` (policy `qwen35-9b-from-evalhub`, 8000) |
| qwen35-9b-wesh | none |

Each model also has `<model>-prometheus-scraping`: monitoring namespaces on
8000 and 9090, openshift-ingress on 8000 and 9002, and **same-namespace pods
on all ports**.

A Praxis pod in another namespace (for example zuno-ai-gateways) cannot reach
the models: the allowed peers are the `ai-gateway` pod label in zuno-ai-run
and the MaaS gateway. A Praxis pod placed in zuno-ai-run could, because the
`-prometheus-scraping` policies open all ports to same-namespace pods.

zuno-redis (zuno-auth, pod label `app.kubernetes.io/name=redis`), policy
`zuno-redis-session-store`:

- TCP 6379 from zuno-ai-run pods `ai-gateway` only
- TCP 9121 (exporter) from openshift-monitoring and openshift-user-workload-monitoring

The namespace default policy in zuno-auth also allows all ports from
same-namespace pods, the ingress policy group, **zuno-ai-run (every pod)**
and zuno-aap. Policies are additive, so any zuno-ai-run pod can reach Redis
through that rule; a Praxis in another namespace could not.

## 7. Free capacity on workers (requests only)

Allocatable minus the sum of pod requests (from `oc describe node`), in
Gi/cores. Actual usage (`oc adm top`) is far lower: for example 25-232 uses
3.9 CPU / 32 GiB. Ephemeral-storage *requests* are almost zero everywhere, so
the free ephemeral figure equals allocatable; real disk usage was not
measured.

| Node | Pool, taint | CPU free | Memory free | Ephemeral allocatable | Fits 4 CPU / 8 Gi / 30 Gi |
|---|---|---|---|---|---|
| ip-10-18-25-232 | general (m5a.4xlarge) | 1.5 | 17.3 Gi | 178 Gi | **no (CPU)** |
| ip-10-18-48-105 | general | 2.1 | 25.6 Gi | 178 Gi (75 Gi requested) | **no (CPU)** |
| ip-10-18-84-138 | general | 1.9 | 20.0 Gi | 178 Gi | **no (CPU)** |
| ip-10-18-18-19 | gpu (g7e.4xlarge), PreferNoSchedule | 10.0 | 83.2 Gi | 223 Gi | yes |
| ip-10-18-31-154 | gpu, PreferNoSchedule | 10.9 | 97.3 Gi | 223 Gi | yes |
| ip-10-18-17-173 | infra (m5a.2xlarge), NoSchedule | 6.7 | 10.4 Gi | 133 Gi | yes, with infra toleration |
| ip-10-18-39-172 | infra, NoSchedule | 6.4 | 14.7 Gi | 133 Gi | yes, with infra toleration |
| ip-10-18-82-70 | infra, NoSchedule | 4.7 | 19.2 Gi | 133 Gi (32 Gi requested) | yes, with infra toleration |

The three general workers are CPU-requests-bound (86-90 % requested; limits
overcommitted two to twenty times). A 4 CPU / 8 Gi build pod with no
toleration will not schedule on them; it would land on a GPU worker (soft
taint) next to the models, which has memory-bandwidth and CPU-contention
implications for serving. Lowering the build request to 1.5 CPU would fit the
general nodes, and the infra nodes need an explicit toleration.
