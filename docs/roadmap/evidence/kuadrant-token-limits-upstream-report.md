# Kuadrant upstream report: token limits beyond the first two are never counted

Status: drafted 2026-10-25, **not filed**. Written to be filed as an issue on the Kuadrant wasm-shim / TokenRateLimitPolicy project; whether and when is a user decision. Reproduced on demo333 (see [wp-157-inventory.md](wp-157-inventory.md), follow-up of 2026-10-25).

Generic on purpose: no cluster, host or token names.

## Summary

When several `TokenRateLimitPolicy` limits apply to the same HTTPRoute (one policy on the Gateway with
`strategy: merge`, plus per-route policies), only the limits that come first in the generated wasm action
set update their Limitador counters. Limits that come later are checked but their counters are never
created or incremented. The same wasm-shim log line appears about once per request:

    kuadrant_wasm_shim: proxy_on_grpc_receive invalid context_id, no match found

and, for some error responses, `Missing json property: /usage/total_tokens` followed by `Task failed`.
The effect is silent: the policy is `Accepted` and `Enforced`, the limit is present in Limitador's
`/limits/<namespace>`, and a request is simply not counted against it.

## Environment (generic)

- Kuadrant operator with Limitador (in-memory storage) and Authorino on OpenShift with the OpenShift
  Gateway API (Istio). Versions to be filled in by whoever files this.
- Gateway with a TokenRateLimitPolicy (`defaults`, `strategy: merge`) carrying two limits, and six
  per-route TokenRateLimitPolicies generated by a controller (one limit per subscription, four per route).
- Requests are non-streaming and streaming OpenAI-style chat completions; the token usage is read from the
  response body.

## Observations

1. Per route the wasm config holds one `ratelimit-check` and one `ratelimit-report` action per limit,
   in a single action set (13 actions with the auth action). Two limits of the gateway-level policy and
   four of the route-level policies on the same route: 6 limits.
2. The order of the limits in the action set follows the limit NAME (alphabetical), not the order in the
   YAML. Changing only the name of a limit moved it in the action set.
3. Experiments with the same traffic, same headers, same Limitador pod (no restart between the first three):
   - order A: route limits first, then limit G (group), then limit U (user): route limits and G count,
     U never has a counter.
   - order B: U first, route limits, G last: U and the route limits count, G never has a counter.
   - order C: G, U, then the four route limits: G and U count, the route limit for the matching
     subscription stops counting (its counter stays constant, for another route it is never created).
   Taken together, the first two limit pairs of the action set are processed, the later ones are not.
   (Hypothesis only: we did not read the shim source; a limit on in-flight gRPC calls or a context that
   ends before the last report answers arrive would give this pattern.)
4. The limit definitions in Limitador for the "missing" limits are identical in shape to the ones that
   count (same conditions pattern, same variables pattern); only the name, the hash and the header differ.
5. A request that crosses a limit is admitted and charged after the response, as documented. The 429
   returned by the gateway is `text/plain` ("Too Many Requests") with no `Retry-After`.

## Minimal reproduction (confirmed)

Throwaway Gateway (istio class) + HTTPRoute to a stub backend returning an OpenAI-style `usage`
(`total_tokens: 100`), one TokenRateLimitPolicy on the Gateway (`defaults`, `strategy: merge`) with four
limits `l1`..`l4`, each `1000000 / 1h`, counter `request.headers['x-test-N']`, predicate
`'x-test-N' in request.headers`. Policy status: Accepted, Enforced.

1. Ten POSTs, each with the four headers (distinct values). All 200.
2. `GET /counters/<route scope>` on Limitador: 20 counters, only `l1` (10) and `l2` (10). `l3` and `l4`: none.
   The gateway proxy logged `invalid context_id` ten times.
3. Rename `l1` to `z1`, ten more requests: counted limits are now `l2` (20) and `l3` (10); `l4` and `z1` have
   no counter. The counted set follows the sorted limit names: the first two only.

## What would help

- Confirmation of whether the shim limits the number of limit pairs it completes per request, and if so a
  documented ceiling, or a fix so that every limit of the action set is reported.
- A status condition or a log at warning level naming the limit that was skipped, instead of a generic
  `invalid context_id`.
- Documentation that the limit name determines the evaluation order within the merged policy.

## Impact

Rate limits that are present, accepted and enforced according to the status do not apply to requests
as soon as a route carries more than about two token limits, with no error on the request path.
