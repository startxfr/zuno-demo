# WP-122: Close the MaaS gateway's missing Keycloak identity source

- **State:** Not started (2026-09-03).
- **ADRs:** ADR-0537 (Decision 3/4 - the same `maas-controller` operator
  immaturity class this WP extends with a second, distinct symptom); ADR-0521
  (the local-model MaaS cutover whose per-group `MaaSSubscription`
  governance this defect silently defeats for every real caller).
- **Depends on:** none.
- **Related:** WP-112 (where this was found, as a live side-effect while
  verifying a Comage fix - out of that WP's own scope, split out here);
  WP-106 (ADR-0537's own WP, same operator, a different confirmed
  `maas-controller` route-identity defect on `ExternalModel`).
- **Target:** v0.7.

## Goal

`ai-gateway`'s MaaS-routed local-model providers (`local-wesh-maas`,
`local-gpt-oss-maas`, `local-maas`, `local-qwen35-maas`) reject **every**
real persona-authenticated call with `401 Unauthorized`, live-confirmed
2026-09-02/03 across multiple agents (Comage, Tekos, others) and multiple
real, freshly-minted Keycloak tokens. Callers silently fall through the
documented provider-fallback chain (ADR-0020/0021) to the same model's
direct/unrouted endpoint, so end users see no visible error - but
ADR-0521's whole point, per-group `MaaSSubscription` token-budget
enforcement, is currently not exercised by any real traffic at all, only
by whatever synthetic/admin-token testing happens to be used to
"verify" it. This WP root-causes and, if repo-side fixable, closes that
gap; if it is genuinely upstream-blocked like ADR-0537's own
`ExternalModel` finding, this WP's job is to document that precisely
(the same rigor ADR-0537 already applied) rather than leave a silently
broken governance control undocumented.

## Live evidence already gathered (2026-09-02/03, do not re-derive)

- `maas-gateway-auth` AuthPolicy (`openshift-ingress`, generated by
  `maas-controller` from RHOAI's `ModelsAsService`/`Tenant` CRs) reports
  `Accepted=True`/`Enforced=True` (the exact "green lies" shape ADR-0511/
  WP-54 already found once for Kuadrant) while
  `spec.defaults.rules.authentication` carries only two identity sources -
  `api-keys` and `openshift-identities` (`kubernetesTokenReview`). No
  Keycloak/OIDC identity source exists at all.
- `gitops/charts/keycloak/files/realm-zuno.json` was amended (`7362b591`)
  to add a `zuno-admin-api` audience mapper to every persona frontend
  client, matching `gitops/charts/models/templates/maas.yaml`'s own
  pre-existing (now-corrected, `327fc246`) comment theorizing a strict
  audience-match rejection. Live-verified insufficient on its own: a
  freshly-minted token still 401s.
- Discriminating test (proposed by a peer session, executed live): forced
  `ModelsAsService.metadata.generation` 2->4 via two real spec edits.
  `status.observedGeneration` correctly advanced to 4, `phase: Ready` -
  the operator processed it - but `maas-gateway-auth`'s own
  `.metadata.generation` and `Enforced` condition timestamp never moved.
  The operator observes `ModelsAsService.spec.externalOIDC` and does
  nothing with it for the AuthPolicy. Not a crash-loop/timing artifact
  (`maas-controller` does crash-loop on leader-election API-server
  timeouts, ~51 restarts/7d, but this specific reconcile ran to a status
  write 66s after its most recent restart - too clean a run to be an
  interrupted write).
- **New lead, not yet tested live (permission-gated, see Preconditions):**
  the `Tenant` CRD (`maas.opendatahub.io/v1alpha1`) has its own
  `spec.externalOIDC.{issuerUrl,clientId,ttl}` - same shape as
  `ModelsAsService`'s. This chart's own `Tenant` CR
  (`gitops/charts/models/templates/maas.yaml`, `zuno-ai-run` namespace)
  is already documented inert since 2026-09-01 (a different, real
  `Tenant` object in namespace `models-as-a-service`, owned by `Config/
  default`, entirely outside this repo's GitOps, is the one
  `maas-controller` actually reconciles - confirmed via its own
  reconcile logs: `"tenant":"models-as-a-service/default-tenant"`).
  Live-checked 2026-09-03: that real `Tenant`'s `spec.externalOIDC` is
  simply **absent**. A public search on `models-as-a-service`'s own docs
  independently describes `externalOIDC` as "configures an external OIDC
  identity provider for the maas-api AuthPolicy" in the context of the
  Tenant resource specifically - consistent with `ModelsAsService`'s own
  copy of this field being the wrong one to set.

## Steps

1. **Test the Tenant-side `externalOIDC` hypothesis live** (the concrete
   next action, pending the approval above):
   `oc patch tenant default-tenant -n models-as-a-service --type merge -p
   '{"spec":{"externalOIDC":{"issuerUrl":"https://keycloak.<cluster-domain>/realms/zuno","clientId":"zuno-admin-api"}}}'`,
   then check whether `maas-gateway-auth`'s
   `spec.defaults.rules.authentication` gains a third (OIDC) identity
   source, and whether a **freshly-minted real persona token**
   (`evaluations/*/run_scenarios.py`'s `get_token()` pattern, not `oc
   whoami -t` - ADR-0201's own documented trap) gets a real `200` through
   `local-wesh-maas`/`local-gpt-oss-maas` instead of `401`.
2. **If it works**: determine a durable, GitOps-owned way to set it -
   check whether the operator reverts a manual `oc patch` on its own next
   reconcile (test by waiting a few minutes and re-checking), and whether
   RHOAI's `DataScienceCluster`/MaaS `Config` CR exposes a
   declarative surface for `Tenant.spec.externalOIDC` this repo could
   template instead of hand-patching a resource it doesn't own. If no
   GitOps-declarable path exists, document the manual step precisely
   (namespace, exact patch, what re-triggers it) as an accepted
   operational gap, the same honesty ADR-0537 already models for its own
   `ExternalModel` finding.
3. **If it does NOT work**: this becomes a second, distinct, confirmed
   `maas-controller` capability gap (externalOIDC never becoming an
   Authorino identity source on any CR that carries it) alongside
   ADR-0537's own `ExternalModel` route-identity one. Search
   `opendatahub-io/models-as-a-service`'s GitHub issues the same way
   ADR-0537 did (issues #1417/#1399/#1240 already found there) for a
   matching known issue; if none exists, document this as a new,
   currently-unfiled upstream gap rather than assume one exists.
4. **Either outcome**: amend ADR-0537 (not a new ADR - same operator,
   same "Proposed" status, same "known upstream `maas-controller`
   defect" framing already established there) with this second finding,
   mirroring its own Decision 3 correction style. Update this WP's own
   Consequences-equivalent section with the real, live-tested outcome.
5. Update `evaluations/comage/security_checks.py`'s
   `comage_chat_uses_photorealistic_images_only_for_marketing_visual_requests`
   and `evaluations/comage/stress_test.py::img-mockup_request` results as
   a downstream confirmation once (if) this closes - WP-112's own
   "Live verification" section already names these as the checks to
   re-run, do not duplicate that tracking here, just update WP-112's
   State once this WP's fix (if any) lands.
