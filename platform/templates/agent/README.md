# Agent onboarding template (ADR-0307)

Self-service scaffold for a new agent: `scaffold_agent.py` writes a real
OKF bundle skeleton, a CR-managed GitOps chart (reusing ADR-0327/ADR-0308's
`aiagent-operator` substrate from day one), and a 20-scenario evaluation
skeleton into the real repository tree. The sixth demo agent
(`agents/naveo/`, ADR-0306/WP-41 Part B) is the permanent proof this
actually works, generated by this exact tool.

## Workflow

1. **Confirm no new domain/backend is needed.** Every `--knowledge`/`--tool`
   value must already exist (`knowledge/*/domain.yaml`,
   `platform/bindings/tools/tool-bindings.yaml`) - self-service onboarding
   composes existing platform capabilities, it does not invent new ones
   (that's a separate ADR-0202/ADR-0116-style proposal).
2. **Run the generator**:

   ```bash
   python3 platform/templates/agent/scaffold_agent.py \
       --name <slug> --title <Title> \
       --description "..." \
       --primary-task <task-slug> --primary-task-title "..." \
       --knowledge knowledge.tech [--knowledge ...] \
       --tool search_confluence [--tool ...] \
       [--live-read-tool <one of --tool>] \
       --business-role consultant \
       --tile-description "..."
   ```

   See `scaffold_agent.py`'s own module docstring for the full flag list
   and defaults (`--entitlement-group` defaults to `agent_<slug>`,
   `--classification` defaults to `C1`, `--sync-wave` defaults to `-96` -
   override to land after whatever the most-recently-added agent used).
3. **Read `agents/<slug>/NEXT_STEPS.md`** - the generator's own checklist
   of everything that still needs a human: prose review, the Keycloak
   fragment merge, `policies/tools/tool-policy.yaml` /
   `policies/knowledge/knowledge-policy.yaml` entries (never
   auto-written - see `scaffold_agent.py`'s own docstring for why: both
   files are hand-curated and densely commented, and a programmatic
   YAML round-trip would silently destroy every comment), and the
   `ansible/roles/agents/tasks/check.yml` smoke-test entry.
4. **Validate** (the same composed validators this template's own CI test
   runs against a throwaway scaffold - see `test_scaffold_validate_discard.py`):

   ```bash
   python3 platform/supply-chain/validate_okf_bundle.py
   python3 platform/docs/check_knowledge_refs.py
   python3 operator/aiagent-operator/validate_contract.py
   python3 platform/docs/check_docs.py
   helm lint gitops/charts/<slug>/
   ```
5. **Open the PR.** The diff is entirely new files (never a change to an
   existing agent's own bundle/chart/evaluation) plus the hand-merged
   Keycloak/policy entries from step 3.
6. **Human review checkpoint** on the persona and the 20 scenarios
   (ADR-0326's own completion pattern - identical bar to every hand-built
   agent).
7. **Operator**: deploy via the `AIAgent` CR, run the 75% gate, flip
   `zuno.status` to `active`.

## What the generator does NOT do

- Does not touch `policies/tools/tool-policy.yaml` or
  `policies/knowledge/knowledge-policy.yaml` (step 3 above).
- Does not touch `gitops/charts/keycloak/files/realm-zuno.json` (emits
  `agents/<slug>/keycloak-fragment.json` instead - a human merges it,
  using any existing agent's own realm entries as the worked example).
- Does not select which existing personas should also gain the new
  entitlement (a judgment call the NEXT_STEPS.md checklist flags but
  does not make).
- Does not flip `zuno.status` to `active` - that is always the
  operator's own step, after a live gate passes, for every agent
  regardless of how it was authored.

## Files

- `scaffold_agent.py` - the generator (`AgentSpec` dataclass + one
  `render_*` function per output file type + `write_all()`).
- `test_scaffold_validate_discard.py` - the ADR-0307 CI acceptance test:
  scaffolds a throwaway agent (`zzz-scaffold-ci-test`), runs the composed
  validators against it, and always deletes it afterward (even on
  failure) - wired into `.github/workflows/lint.yml`.
