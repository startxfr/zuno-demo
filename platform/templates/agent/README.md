# Agent onboarding template (ADR-0307)

Self-service scaffold for the platform half of a new agent:
`scaffold_agent.py` writes a 20-scenario evaluation skeleton into
`evaluations/<slug>/`. Since WP-156 it generates no chart, Application or
AIAgent CR: the AIAgent operator, agent-frontend and agent-bff were
retired, and UnifAI serves an agent from its OKF bundle once a
zuno-demo-agents release carrying it is admitted (ADR-0561, ADR-0580).
Since WP-165 it generates no bundle either: bundles, entitlement groups and
corp policy entries are authored in zuno-demo-agents (ADR-0576), with that
repository's own scaffold. The sixth demo agent (naveo, ADR-0410/WP-41
Part B) was generated by this tool before the split.

## Workflow

1. **Confirm no new domain/backend is needed.** Every `--knowledge`/`--tool`
   value must already exist (`knowledge/*/domain.yaml`,
   `platform/bindings/tools/tool-bindings.yaml`) - self-service onboarding
   composes existing platform capabilities, it does not invent new ones
   (that's a separate ADR-0202/ADR-0116-style proposal). Admission enforces
   it: a release whose agent reaches an unbound tool or domain is refused.
2. **Author the bundle in zuno-demo-agents** and tag a release there.
3. **Run the generator** here for the evaluation skeleton:

   ```bash
   python3 platform/templates/agent/scaffold_agent.py \
       --name <slug> --title <Title> \
       --description "..." \
       --primary-task <task-slug> --primary-task-title "..." \
       --knowledge knowledge.tech [--knowledge ...] \
       --tool search_confluence [--tool ...] \
       [--live-read-tool <one of --tool>] \
       --business-role consultant \
       --tile-description "..."
   ```

   See `scaffold_agent.py`'s own module docstring for the full flag list
   and defaults (`--entitlement-group` defaults to `agent_<slug>`,
   `--classification` defaults to `C1`).
4. **Read `evaluations/<slug>/NEXT_STEPS.md`** - the generator's own
   checklist of everything that still needs a human.
5. **Admit the release** carrying the bundle (`make d3 admit agents
   RELEASE=vX.Y.Z UPDATE_LOCK=1`, or merge the promotion PR), regenerate
   `platform/okf/stack-config.generated.yaml`, and validate:

   ```bash
   python3 platform/docs/check_knowledge_refs.py
   python3 platform/docs/check_docs.py
   ```
6. **Human review checkpoint** on the persona and the 20 scenarios
   (ADR-0326's own completion pattern - identical bar to every hand-built
   agent).
7. **Operator**: deploy it with `make d2 install unifai`, run the 75% gate,
   flip `zuno.status` to `active` in zuno-demo-agents and promote that
   release.

## What the generator does NOT do

- Does not write the OKF bundle, the Keycloak entitlement group or the
  corp policy entries (zuno-demo-agents; the group is generated from the
  release, ADR-0581, and reconciled by the ADR-0530 Job).
- Does not select which existing personas should also gain the new
  entitlement (a judgment call, user administration in Keycloak).
- Does not flip `zuno.status` to `active` - that is always the
  operator's own step, after a live gate passes, for every agent
  regardless of how it was authored.

## Files

- `scaffold_agent.py` - the generator (`AgentSpec` dataclass + one
  `render_*` function per output file type + `write_all()`).
- `test_scaffold_validate_discard.py` - the ADR-0307 CI acceptance test:
  scaffolds a throwaway agent (`zzz-scaffold-ci-test`), checks the
  generated files compile and parse, and always deletes it afterward (even
  on failure) - wired into `.github/workflows/lint.yml`.
